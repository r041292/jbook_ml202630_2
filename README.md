# Dashboard de Precálculo

Proyecto académico de Machine Learning de la Universidad del Norte. Explora los datos reales del nivelatorio de Precálculo en ALEK y compara modelos de regresión para predecir la **nota del primer parcial** (escala 0–5). El dashboard presenta la validación cruzada externa por estudiante, el contraste en un periodo temporal reservado, la comparación estadística de los modelos frente al SVM lineal y un simulador de predicción con el pipeline de Kernel Ridge RBF.

**Autores:** Rubiel Velásquez y Valentina Figueroa.

>
> Es el informe técnico final del proyecto, organizado en el formato que pide la guía del Tercer Entregable: introducción, datos (ETL y EDA), modelos benchmark y sus mejores combinaciones, revisión de literatura y novedad, modelos originales (KRR centrado, TN-KRR y GPR–XGBoost), validación estadística, dashboard y despliegue, conclusiones, y reproducibilidad con bibliografía. Su código y sus tablas están en [`jbook_dashboard_e4_final/`](jbook_dashboard_e4_final/). El Jupyter Book anterior del dashboard se conserva en la raíz del sitio como informe complementario.

## Datos y protocolo

- **Fuente:** 1.527 registros de 1.506 estudiantes en seis periodos (2023–2025). Tras excluir las filas sin objetivo quedan 1.497 registros válidos y 15 variables predictoras. `nota_final` nunca se usa como predictora.
- **Partición:** el periodo 202530 (188 registros) se reserva como **test temporal**; el entrenamiento son 1.309 registros de 1.293 estudiantes de los periodos anteriores.
- **Validación:** `GroupKFold` anidado por estudiante, con cinco folds externos y cinco internos. El preprocesamiento se aprende dentro de cada fold y **el test nunca selecciona hiperparámetros ni modelos**.
- **Búsqueda de hiperparámetros:** Grid Search, Random Search, Optuna/TPE, DEAP (genética) y Successive Halving. Cada entrenamiento externo elige método y parámetros por RMSE interno, y el procedimiento se repite en todo el entrenamiento para el ajuste final. El tiempo no interviene en la selección.
- **Comparación estadística:** prueba de Friedman, post hoc de Nemenyi y Model Confidence Set, contraste tipo Diebold–Mariano por estudiante frente al SVM con corrección HLN (adaptado a este diseño) y tamaños de efecto. Con cinco folds dependientes la evidencia es **exploratoria**.

## Resultados vigentes

- **Kernel Ridge RBF** tiene el menor RMSE medio de validación cruzada entre los modelos originales (0,8010) y es el único modelo al que el dashboard le calcula SHAP (por permutaciones) y LIME. GPR–XGBoost obtiene el menor RMSE en el test (0,9029).
- Kernel Ridge RBF, GPR–XGBoost, TR-KRR y SVR RBF forman el conjunto del Model Confidence Set y no se distinguen entre sí. Frente al SVM mejoran en la prueba por estudiante, pero la prueba conservadora (t corregida) no confirma esa mejora: es una indicación exploratoria, no una demostración.
- En los modelos clásicos, ningún modelo supera significativamente al SVM lineal.

## Índice de archivos de referencia por modelo

Cada enlace lleva a GitHub. Para cada modelo se listan los archivos que intervienen en su entrenamiento, en este orden: el script que lo ejecuta, la búsqueda de hiperparámetros, el módulo que **define** el modelo y los datos y la partición comunes. Los scripts que ejecutan el ajuste (`fit`) no definen los modelos, los importan; por eso se listan los módulos importados que sí participan en el entrenamiento de ese modelo, con lo que contienen. No se incluyen archivos que el script importa para otros modelos (por ejemplo, `evaluar_busquedas_e3.py` importa el árbol de decisión para construir su tabla conjunta, pero el SVM no lo usa). Los modelos de librería conservan su ejecución histórica y no tienen búsqueda nueva. Resultados en [`Precalculo/resultados/e3/`](https://github.com/r041292/jbook_ml202630_2/blob/main/Precalculo/resultados/e3) y tiempos en [`TIEMPOS_EJECUCION.md`](TIEMPOS_EJECUCION.md).

Para replicar el entrenamiento hace falta lo siguiente. **Entorno:** instalar PyTorch para CPU (`torch==2.9.1`) y después `Precalculo/requirements.txt`, más `Precalculo/requirements_busquedas_e3.txt` (Optuna y DEAP) en el mismo entorno. Todos estos requisitos son necesarios solo si se quiere ejecutar **todo**, incluidos los modelos de librería y preentrenados: por eso se solicita PyTorch, que usan TabPFN, TabICLv2, TabFM y RIM. Quien solo quiera reentrenar SVM, clásicos y los originales de kernel (SVR RBF, Kernel Ridge y TR-KRR) puede prescindir de los requisitos propios de los modelos de librería (`requirements_scopus_e3.txt`, `requirements_tabfm_e3.txt`, `requirements_tabpfn25.txt` y `requirements_svr_rbf_raffle_e3.txt`). **Datos:** los datos reales deben estar en `Precalculo/Data/Datos_Brutos.csv` junto a `cabeceras.csv`. Los scripts comparan el hash de la fuente con el de los reportes y se detienen si cambió.

**Orden de ejecución,** siempre desde la carpeta `Precalculo/` y con semilla 42:

- **Paso 1 · `entregable3.py`:** genera la partición (test 202530), el SVM base y las exportaciones canónicas de train y test.
- **Paso 2 · `modelos_clasicos.py` y `evaluar_decision_tree_e3.py`:** entrenan los clásicos y el árbol sobre los mismos folds. Las multibúsquedas leen y verifican estas exportaciones, por lo que deben existir antes.
- **Paso 3 · `evaluar_busquedas_e3.py`:** reentrena SVM y clásicos con las cinco estrategias y crea `resultados/e3/busquedas/<run_id>`. Luego se activa con `activar_busqueda_e3.py <run_id>`.
- **Paso 4 · `evaluar_originales_busquedas_e3.py`:** entrena los originales y reutiliza la ejecución activa de SVM y clásicos. Por defecto ejecuta SVR RBF, Kernel Ridge y TR-KRR; los demás se piden con `--models` (por ejemplo `--models m3 m7`), con `--allow-large-grid` para las grillas grandes.
- **Paso 5 · modelos de librería (opcional):** cada uno conserva su ejecución histórica y se corre con su propio script de la tabla. Requieren checkpoints locales: TabPFN (`descargar_tabpfn25.py`), TabICLv2, TabFM, el paquete *fine-tuned* y el código de coPILOT en `terceros/wPILOT`.

Las búsquedas usan 4 procesos con un hilo cada uno y nunca seleccionan con el test. `model_timing.py` vive en `Dash/` y `evaluar_busquedas_e3.py` lo importa sin añadir la ruta, por lo que conviene incluir `Dash/` en el `PYTHONPATH`. Los pasos detallados y los comandos están en [`README_E3.md`](https://github.com/r041292/jbook_ml202630_2/blob/main/Precalculo/README_E3.md).

## Ejecución local

El proyecto usa un único entorno virtual, `Precalculo/venv/`. Con él instalado y activo, desde la raíz del repositorio:

```bash
pip install -r Dash/requirements.txt
cd Dash
python app.py
```

El dashboard queda en `http://127.0.0.1:8050/`. Para construir el informe:

```bash
cd jbook_dashboard
BASE_URL=/jbook_ml202630_2 jupyter-book build --html --strict
```
